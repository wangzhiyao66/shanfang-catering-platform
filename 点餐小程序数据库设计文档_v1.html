点餐小程序 · 后端数据库设计文档 v1

场景：中餐单店 · 三端共用一套数据库（小程序顾客端 / 商家后台 / 后厨端） · 版本 2026-08-15

1. 设计目标与原则

本设计回答四个问题：要建几张表、表之间怎么关联、有哪些边界、同一套库如何同时兼容小程序端和后台。

一套库，三端共享
小程序、后台、后厨读写同一份数据，不存在"两套数据"。
按域建模
菜单 / 桌台 / 会员 / 订单 / 后厨 / 营销 / 权限 各域解耦，靠订单主表聚合。
状态机驱动
订单、桌台、支付等核心实体用明确状态机约束合法流转。
可扩展
带 shop_id 租户字段，单店起步、未来可平滑升级连锁。

技术选型建议：关系型数据库 MySQL 8.0（或 PostgreSQL 14）；高频/临时数据（桌台实时状态、购物车、排队号）放 Redis；图片/菜单图走对象存储（COS/OSS）。以下表定义以 MySQL 风格为例。

2. 总体架构

三层表现（小程序 / 后台 Web / 后厨 KDS）通过统一的 API 网关 + 鉴权层 访问同一业务服务与同一数据库。数据库是唯一的"事实来源"。

┌────────────┐   ┌────────────┐   ┌──────────┐
│ 小程序(顾客)│   │ 后台(商家) │   │ 后厨(KDS)│
└─────┬──────┘   └─────┬──────┘   └────┬─────┘
      │  /api/client/*  │ /api/admin/*  │ /api/kitchen/*
      └────────┬────────┴───────┬────────┘
               ▼                ▼
         ┌─────────────── 鉴权 & 路由网关 ───────────────┐
         │  小程序: openid→member  |  后台: staff→role    │
         └────────────────────┬──────────────────────────┘
                              ▼
                  业务服务层（Service / DAO 共用）
                              ▼
        ┌──────────── 主库 MySQL ────────────┐  ┌─ Redis ─┐
        │  26 张表（同库，按 shop_id 隔离）    │  │状态/购物车│
        └────────────────────────────────────┘  └─────────┘

关键认知：三端不是三套库，而是 同一库的三种访问视角。小程序只看见"自己的订单 + 公开菜单"；后台看见"全店数据"；后厨只看见"本档口的出单"。

3. 表总览（26 张）

按业务域分组。优先级：P0 必做P1 进阶P2 远期

门店/菜单

  • shop 门店 P0 — 店铺基本信息、营业时间、支付参数引用
  • category 菜品分类 P0 — 热菜/凉菜/汤品/主食/小吃/饮品
  • dish 菜品 P0 — 名称、基础价、状态、是否称重、默认辣度
  • dish_spec 规格组 P0 — 份量 / 辣度 / 忌口（如"份量"是一个组）
  • dish_spec_option 规格选项 P0 — 大/小/半份；微/中/特/免
  • dish_sku 菜品售卖单元 P0 — 规格组合对应唯一价格与库存

桌台/场景

  • dining_table 桌台 P0 — 桌号、区域(大厅/包间)、座位数、状态、二维码
  • reservation 预订/包间 P1 — 日期、时段、人数、包间、订金
  • queue 排队 P1 — 取号、人数、叫号、状态

会员/顾客

  • member 会员 P0 — 微信 openid、手机号、昵称、等级、积分、余额
  • member_level 会员等级 P1 — 等级名、折扣、升级门槛
  • member_address 会员地址 P1 — 外卖/自提收货地址
  • points_log 积分流水 P1 — 获得/消耗记录（审计）
  • balance_log 储值流水 P2 — 充值/消费记录

订单/交易

  • cart 购物车 P0 — 多人合单用，绑定桌台+成员
  • cart_item 购物车明细 P0 — 菜品/规格/数量/备注
  • order 订单主表 P0 — 订单号、类型(堂食/外卖/自提)、状态、金额
  • order_item 订单明细 P0 — 同 cart_item，落定快照（含规格JSON、备注、辣度）
  • order_payment 支付记录 P0 — 微信支付流水、状态、幂等

后厨/履约

  • kitchen_station 档口 P0 — 热菜/凉菜/饮品等出单口
  • kitchen_ticket 厨打分单 P0 — 订单按档口拆分出的出单，状态独立
  • printer 打印机 P1 — 各档口/总台打印机配置

营销

  • coupon_template 优惠券模板 P1 — 满减/折扣规则
  • coupon 用户优惠券 P1 — 发放到具体会员的券
  • promotion 促销活动 P2 — 秒杀/拼团/满赠

权限/员工 & 配置

  • staff 员工账号 P0 — 老板/店长/服务员/后厨，角色外键
  • role 角色 P0 — 权限集合（功能+数据范围）
  • review 评价 P1 — 订单/菜品评分与留言
  • config 系统配置 P0 — 营业时间、分单规则、小程序开关
  • operation_log 操作日志 P1 — 后台关键操作审计

6. 关键边界设计

① 业务边界（域解耦）

菜单域、交易域、履约域、会员域、营销域、权限域各自独立建表，通过 order 主表作为"聚合根"串起来。跨域操作（如"下单后推后厨分单"）由服务层事务保证，不在数据库层硬耦合。好处：改菜单价不影响历史订单（订单明细已快照）。

② 数据边界（隔离 / 软删 / 审计）
  • 租户隔离：每张业务表带 shop_id，所有查询必须带该条件，单店与未来连锁共用同一套结构。
  • 软删除：统一 deleted_at，不物理删，便于对账与恢复（订单/会员/菜品永不物理删）。
  • 快照：order_item 存 dish_name / unit_price / specs_json 落定快照，菜品后续改名改价不影响历史账单。
  • 审计：operation_log + points_log / balance_log 记录资金与权益变动，可追溯。
③ 并发边界（防超卖 / 重复支付 / 重复接单）
  • 乐观锁：order.version、dining_table.version 更新时校验版本，失败重试。
  • 幂等：order.order_no、order_payment.pay_no 唯一索引，重复提交直接返回原结果。
  • 状态机约束：状态只许按合法路径流转（见下），非法变更在 service 层拒绝。
  • 分布式锁：接单、改桌台状态、库存扣减用 Redis 锁，避免多服务员同时操作冲突。
④ 金额边界（分单位 + 服务端计算）
  • 所有金额用 INT（分） 存储与传输，杜绝浮点误差；前端仅做 ÷100 展示。
  • 优惠（满减/折扣/券/会员折扣）全部在 服务端计算，pay_amount = total - discount，前端传的"优惠金额"只作展示、不被信任。
  • 退款走 order_payment 新记录（status=3），原支付保留，账目清晰。
⑤ 状态机边界（核心实体）

order.status（同表承载堂食/外卖/自提，状态语义一致）：

待支付(0) → 已支付/待接单(1) → 制作中(2) → 已上菜/待取餐(3)
   → 已完成(4) ─┐
待支付 ──取消(9)  ├─ 任意非终态 ──退款中(5) ──已退款(6)
制作中/待接单 ──退单(7)

dining_table.status：空闲(0) → 预定(2) → 占用(1) → 清洁中(3) → 空闲(0)
order_payment.status：待支付(0) → 成功(1) / 失败(2) → 退款(3)
kitchen_ticket.status：待做(0) → 制作中(1) → 完成(2) / 退单(3)

非法流转（如"已完成"再改"制作中"）在 service 层用状态机校验拦截。

⑥ 权限边界（谁能看/改什么）
  • 小程序端：只能读写 member_id = 自己 的数据（订单/购物车/优惠券/评价），菜单为公开只读。
  • 后台端：按 role.data_scope 控制——老板/店长全店；服务员仅本桌；后厨仅本档口（kitchen_ticket.station_id 过滤）。
  • 字段级：dish.cost_price、利润类字段只在后台 API 返回，小程序 API 字段白名单剔除。

7. 多端兼容设计（一套库服务小程序 + 后台）

核心思想：数据库与业务服务只有一套，差异只在"接入身份"与"可见范围"。

维度小程序端（顾客）后台管理系统（商家）
接入身份微信 openid → 解析出 member_idstaff + role 登录令牌
数据范围仅 member_id=自己 + 公开菜单全店（按 role.data_scope 收缩）
同表复用order / dish / dining_table / coupon 等同一张表，靠 type、member_id、status 区分场景，不建副本
字段可见性白名单返回（隐藏成本/利润/员工字段）全字段 + 管理字段
写操作下单、加菜、支付、评价、预约改菜单、接单、出餐、退款、配置
实时同步轮询/订阅消息看订单状态KDS/后台长连接看订单与出单
兼容落地的 4 个关键设计
  • ① 路由分层共享服务：/api/client/* 与 /api/admin/* 两套路由，但共用同一 Service / DAO 层与同一数据库——避免逻辑分叉导致数据不一致。
  • ② 场景字段复用：order.type ∈ {1堂食,2外卖,3自提} 让三种业态落在同一订单表与同一状态机；新增业态（如"预约自提"）只需加枚举，不改表结构。
  • ③ 桌台二维码双用：dining_table.qr_token 既被小程序扫码落座，也被后台打印绑定，同一字段服务两端。
  • ④ 状态机单一真相：无论小程序"催菜"还是后台"出餐"，都走同一套 order.status 状态机；两端靠 updated_at/版本号保持一致，杜绝"顾客付了钱后厨不知道"。

由此，所谓"小程序一套、后台一套"在数据库层面不成立——只有一套库。是否"自建"的区别只是：SaaS 帮你把这套表和服务都搭好了；自建则需要按本文档把 26 张表与服务实现出来。

8. 索引与性能建议

  • 唯一索引：order(order_no)、order_payment(pay_no)、coupon(code)、member(openid, shop_id)、dish_sku(spec_path, dish_id)。
  • 普通索引：各表 shop_id；order(shop_id, status, created_at)（报表/待接单列表）；order(member_id)；order(table_id, status)；kitchen_ticket(station_id, status)。
  • Redis 缓存：菜单树（category+dish+sku）、桌台实时状态、购物车、排队号——高读低频写，显著降主库压力。
  • 分表/归档：order / order_payment / operation_log 按月归档，单店日单量不大可先不分。

9. 建表示例（DDL 节选）

仅示例核心表结构（MySQL 8），完整 26 张表按第 5 节字段落地。

CREATE TABLE `order` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `shop_id`       BIGINT NOT NULL,
  `order_no`      VARCHAR(32) NOT NULL,
  `type`          TINYINT NOT NULL DEFAULT 1 COMMENT '1堂食2外卖3自提',
  `member_id`     BIGINT NOT NULL,
  `table_id`      BIGINT DEFAULT NULL,
  `status`        TINYINT NOT NULL DEFAULT 0,
  `people_count`  INT DEFAULT 1,
  `total_amount`  INT NOT NULL DEFAULT 0 COMMENT '分',
  `discount_amount` INT NOT NULL DEFAULT 0,
  `pay_amount`    INT NOT NULL DEFAULT 0,
  `coupon_id`     BIGINT DEFAULT NULL,
  `paid_at`       DATETIME DEFAULT NULL,
  `version`       INT NOT NULL DEFAULT 0,
  `created_at`    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted_at`    DATETIME DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  KEY `idx_shop_status` (`shop_id`,`status`,`created_at`),
  KEY `idx_member` (`member_id`),
  KEY `idx_table` (`table_id`,`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE `kitchen_ticket` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `shop_id`     BIGINT NOT NULL,
  `order_id`    BIGINT NOT NULL,
  `station_id`  BIGINT NOT NULL,
  `printer_id`  BIGINT DEFAULT NULL,
  `items_json`  JSON,
  `status`      TINYINT NOT NULL DEFAULT 0,
  `pushed_at`   DATETIME DEFAULT NULL,
  `done_at`     DATETIME DEFAULT NULL,
  `created_at`  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_station` (`station_id`,`status`),
  KEY `idx_order` (`order_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
