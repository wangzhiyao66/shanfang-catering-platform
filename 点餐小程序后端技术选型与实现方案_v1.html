点餐小程序 · 后端技术选型与实现方案 v1

中餐单店 · 三端共用一套库（小程序顾客端 / 商家后台 / 后厨端） · 配合《数据库设计文档_v1》《PRD_v1》· 已确认走 Java Spring Boot · 2026-08-15
结论（已确认栈）： Java 17 + Spring Boot 3.x 作为后端框架， ORM 用 MyBatis-Plus（内置多租户 + 乐观锁 + 分页，最贴本项目）， 主库 MySQL 8.0，缓存/分布式锁用 Redis + Redisson， 图片走 腾讯云 COS，微信登录/支付用官方 v3 接口封装。 后端监听 3000 端口，路由前缀 /api/client 与 /api/admin 共用同一 Service/DAO 与同一数据库，与小程序 request.js 契约天然对齐。

1. 选型依据（现有文档的硬约束）

  • 已定契约：后端地址 http://localhost:3000/api/client；/api/client/* 与 /api/admin/* 两套路由共用同一 Service/DAO 与同一数据库（数据库文档 §6）。
  • 返回格式：统一 { code:0, data, msg }；401 表示未登录触发重新授权（MiniProgram-web/utils/request.js）。
  • 身份与租户：请求头 X-Openid（解析会员）、X-Shop-Id（租户隔离）；每张业务表带 shop_id。
  • 数据层：关系型 MySQL 8.0（或 PG14）；高频/临时数据放 Redis；图片走对象存储（COS/OSS）。
  • 并发边界：接单、改桌台状态、库存扣减用 Redis 分布式锁；订单状态机用 version 乐观锁（数据库文档 §3、§5）。
  • 外部集成：微信登录（code2session）、微信支付 v3（返回 payParams 供 wx.requestPayment，需回调验签）。
  • 性能目标：午晚市高并发下单；下单→后厨出单 < 3s；页面加载 < 1.5s（PRD）。

3. 为什么 Spring Boot（已选，附取舍）

选 Spring Boot 的优势

  • 餐饮后台生态最成熟：微信支付 v3、ERP/报表、权限(RBAC)、连锁多门店在 Java 社区资料最多，出问题好查。
  • 事务与并发开箱即用：@Transactional 保证"下单→推后厨分单"原子；Redisson 分布式锁、MP 乐观锁直接对标数据库文档的并发边界。
  • 多租户几乎免费：MyBatis-Plus TenantLineInnerInterceptor 自动给每条 SQL 拼 shop_id，从源头杜绝越权——正好命中文档"所有查询必须带 shop_id"。
  • 可演进：未来上连锁、加定时报表、加 WebSocket（后厨 KDS 实时推送）都有现成方案。

需要注意的取舍

  • 与前端语言不同：小程序是 JS，后端是 Java，两端靠 REST 解耦（无影响），但团队需同时具备两种能力。
  • 比 Node 重：启动内存/构建略重，但单店量级完全无压力。
  • 备选提示：若只想最快跑通 demo、且团队只会 JS，可改回 NestJS（Node/TS）——契约同样零摩擦、更轻。确认走 Java 即按本方案推进。

MyBatis-Plus 多租户插件在 MybatisPlusConfig 注册：拦截所有查询自动加 WHERE shop_id = ?（值取自 ShopContext），写操作由 Insert 填充。这样 Service 层无需手写 shop_id 条件，从框架层保证隔离。

5. 关键实现方案（Java 侧）

5.1 统一返回 & 异常处理

// R.java：统一结构
R.ok(data)            → { code:0, data, msg:"ok" }
R.fail(code, msg)     → { code, data:null, msg }
// ResponseAdvice(ResponseBodyAdvice)：成功响应统一包裹为 {code:0,data,msg}
// GlobalExceptionHandler(@RestControllerAdvice)：
//   BizException → {code,msg}；未登录/无 shopId → 401

5.2 鉴权（对齐 request.js）

  • ShopInterceptor：所有请求必带 X-Shop-Id，缺失/非法 → 401；写入 ShopContext。
  • OpenidInterceptor：/api/client 需登录接口读 X-Openid 解析 member；缺失 → 401 触发小程序重新 wx.login。
  • JwtInterceptor：/api/admin 校验后台 JWT（店长/员工账号密码登录签发）。

5.3 微信登录

POST /api/client/auth/login  { code }
  → RestTemplate 调 code2session(appid+secret+code)
  → 查/建 member（openid + shop_id 唯一）
  → 返回 openid / member 基础信息（小程序缓存 globalData）

5.4 微信支付 v3（订单 → 后厨 < 3s）

  • POST /api/client/orders：@Transactional 创建订单（加 Redis 锁扣库存/占桌台 → 写 order + 明细快照 → 推后厨分单）。
  • 返回 payParams：{timeStamp, nonceStr, package, signType, paySign} 供 wx.requestPayment。
  • POST /api/client/pay/notify：用平台证书验签 → 按 out_trade_no 幂等（已支付直接 SUCCESS）→ 置已支付、释放锁。

5.5 并发与一致性

  • Redisson 分布式锁：RLock lock = redissonClient.getLock("order:accept:"+orderId)，接单/改桌台/扣库存加锁，防多服务员并发冲突。
  • 乐观锁：订单实体 @Version private Long version，MP 自动 UPDATE ... WHERE id=? AND version=?，失败重试，防重复接单/改状态。
  • 支付幂等：out_trade_no 唯一 + 已支付校验，回调重复到达安全。

5.6 缓存策略

  • 菜单树（category+dish+sku）缓存 Redis，后台改菜品主动失效——高读低频写，显著降主库压力。
  • 桌台实时状态 / 购物车 / 排队号 放 Redis（带过期）。
  • 归档：order / order_payment / operation_log 按月归档，单店日单量不大可先不分。

5.7 部署与合规

  • 本地：docker-compose 起 mysql + redis，mvn spring-boot:run 监听 3000（与 request.js baseURL 一致）。
  • 生产：打 fat-jar → Docker 镜像 → 腾讯云 轻量/CVM；MySQL、Redis 用 TencentDB 托管；Nginx + HTTPS（微信支付与合法域名均要求 HTTPS）。
  • 小程序后台配置 request 合法域名 指向后端 HTTPS 地址；服务器域名需 ICP 备案。
